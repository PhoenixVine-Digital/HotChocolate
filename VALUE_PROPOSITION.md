# Why Hot Chocolate, instead of just writing Java?

Hot Chocolate compiles to the same JVM bytecode a Minecraft mod or a
JVM-hosted game engine already runs on — same classpath, same `.jar`,
same `java` launcher. Nothing here asks you to leave the JVM game/mod
ecosystem. The pitch is narrower and more concrete than "a better
Java": a handful of features Java structurally cannot offer without
either erasing/boxing your data, letting aliasing bugs through to
runtime, or making you hand-write a wrapper around
`java.util.concurrent` every single time — all three of which are
exactly the classes of bug and boilerplate that show up in real game
and mod code, not in a textbook example.

This document is the "why," aimed at someone deciding whether to reach
for Hot Chocolate on a real project. For syntax and how-to, see
[TUTORIAL.md](TUTORIAL.md); for a short intro, see [README.md](README.md);
for the full reference and design rationale (including honest scope
cuts), see [ARCHITECTURE.md](ARCHITECTURE.md).

## The short version

| | Java | Hot Chocolate |
|---|---|---|
| Generic collection of `Int` | boxes every element to `Integer` | monomorphized — a real `int[]`-shaped `Vec$Int`, no boxing |
| "Can this struct alias/get mutated out from under me?" | found at runtime, if you're lucky | checked at compile time (move/borrow checking) |
| "Can this background task safely capture that data?" | found at runtime (a race), if you're lucky | checked at compile time (`@sendable`) |
| Background task pool | hand-roll `ExecutorService`/`Future`/`CompletableFuture` boilerplate yourself, every project | `PhoenixPool`/`PhoenixVirtualPool`, a few lines, same safety guarantee above |
| Off-heap, cache-friendly game data (particles, ECS components) | manual `java.lang.foreign` `MemorySegment` arithmetic, or eat GC pressure from N heap objects | `arena struct` — declare it, index it, done |
| Targeting three different JDKs (old mod line, new mod line, engine) from one codebase | three separate toolchains/build configs, or lowest-common-denominator code | one compiler, one `--target` flag |
| Modeling "one of several variants, exhaustively" | class hierarchy + `instanceof` chains, or an enum with no payload | sealed interfaces + `match`, exhaustiveness included |
| Calling existing Java/engine APIs | it's Java | direct `extern class`/`extern interface` bindings, zero-cost, no wrapper layer |

Everything below expands one row.

## Real generics that monomorphize — not Java's erase-and-box

Java generics are a compile-time-only fiction: `List<Int>` is really
`List<Object>` with a cast inserted at each read, and every `Int` you
put in gets boxed to an `Integer` — a real heap allocation per element.
For a game's hot path (a component array, a particle list, anything
iterated every frame) that's exactly the GC pressure and cache-miss
cost a game can least afford, and it's invisible at the Java source
level — nothing about `List<Int> xs` looks like it's allocating.

Hot Chocolate's `Vec<T>`/`Registry<T>` and user-written generic
structs/enums genuinely monomorphize: `Vec<Int>` and `Vec<PhoenixTask>`
are two different, specialized classes generated by the compiler, each
storing its element type directly — a `Vec<Int>` really does hold raw
`int`s, no `Integer` boxing, no erasure-driven cast at every access.
You get the ergonomics of writing generic code once, with the memory
layout of having hand-written the specialized version yourself.

## Compile-time move/borrow checking — for the bugs that actually bite in game code

This is the headline feature, and it's aimed at a specific, common
failure mode: game and ECS code is full of structs (entities,
components, game state) getting passed around, stored, and mutated
from multiple places, and Java's type system has nothing to say about
whether that's safe. A struct handed to a function, then used again
afterward assuming it's still yours; a `&mut` alias to something
another system still holds a plain read-only view of — both compile
fine in Java and fail (or silently corrupt state) at runtime, often
far from the actual mistake.

Hot Chocolate's checker enforces this at compile time instead:

- Moving a struct by value and using it again afterward is a real
  compile error, not a runtime surprise.
- `&mut` requires the variable be declared `var` — you can't take a
  mutable reference to something you never declared mutable.
- Mutating through a plain `&` (read-only) reference is a compile
  error.

None of this needs annotations beyond the `&`/`&mut` you'd already
write to express intent — the checker derives the safety property from
syntax you're already using to say what you mean. See "Compile-time
safety roadmap" in ARCHITECTURE.md for the exact rule set (and the honest
scope: this isn't Rust's full memory-safety story — the JVM's GC
already owns memory safety, so this is deliberately narrower, aimed at
aliasing/mutation bugs specifically, not lifetimes).

## `@sendable`: proving a background task can't race before it ever runs

Game engines and mods routinely want work off the main thread — asset
loading, world generation, network I/O — and the classic bug is a
background task capturing a mutable reference to shared state that the
main thread is also touching, discovered as an intermittent, hard-to-
reproduce data race. Java's type system doesn't distinguish "safe to
hand to another thread" from "not" at all; a lambda captures whatever
it captures, and `Runnable`/`Callable` don't know or care.

Hot Chocolate's Phoenix Flight task pool (below) enforces this at
compile time: a lambda passed to `pool.spawn(...)` can only capture
`Copy` primitives, `String`, or a struct explicitly marked
`@sendable` — anything else is a compile error naming exactly what
was captured and why it's unsafe. This is real, load-bearing static
analysis keyed on the lambda's *actual* captures, not a lint that can
be silenced — the check is closer to the "prove parallel access is
safe" analysis a real ECS scheduler eventually needs (see
[ECS_IDEAS.md](ECS_IDEAS.md) for where that's headed) than to anything
Java offers.

## Phoenix Flight: a real task pool, without hand-rolling `java.util.concurrent`

Every JVM game/mod project that wants background work ends up writing
its own thin wrapper around `ExecutorService`/`Future`/
`CompletableFuture` — and re-deriving the same lifecycle bugs (forgot
`shutdown()`, so the JVM never exits; a task's exception getting
wrapped in `ExecutionException` instead of the real cause) every time.
Hot Chocolate ships this once, as language-level stdlib, with the
`@sendable` safety guarantee above built in for free:

```
use phoenix;

fn main() {
    let pool = PhoenixPool::new(4);
    let task = pool.spawn(|| expensive_computation() as PhoenixObject);
    let result = task.join() as Int; // real box/unbox, not just String round-tripping
    pool.shutdown();
}
```

- Real async chaining (`spawn_chain`/`.then(...)`, backed by
  `CompletableFuture`) for "run this, then that, with nothing blocking
  in between."
- Dependency-ordered spawning (`spawn_after`/`spawn_after_all`) for the
  simpler "wait for this, then run that" shape.
- `join()` re-throws the task's *real* exception, not Java's
  `ExecutionException` wrapper — a `catch` around `task.join()` behaves
  exactly like a synchronous call would.
- `join_all_and_shutdown` bundles the "spawn several, wait for all,
  shut down" lifecycle so forgetting `shutdown()` (and hanging the
  process on non-daemon threads) isn't on you to remember.
- `PhoenixVirtualPool` (`use phoenix_virtual;`, `--target 21`+) wraps
  JDK 21's virtual threads with the identical API — cheap, massively
  concurrent I/O-bound tasks (asset streaming, many concurrent network
  calls) without switching mental models.

This is the actual point of it existing as more than a wrapper: the
capture-safety check above is real, compiler-enforced concurrency
safety Java's own `ExecutorService` API gives you zero help with.

## Off-heap, cache-friendly game data — without hand-writing `java.lang.foreign`

Hot-path game data — particles, ECS components, spatial grids — wants
to live in one contiguous block of memory, not as thousands of separate
GC-tracked heap objects. The JDK's Foreign Memory API
(`java.lang.foreign`, stable since JDK 22) can do this, but using it
directly means hand-writing `MemorySegment` arithmetic, manual
`ValueLayout` bookkeeping, and getting the offset math right yourself
for every struct shape.

Hot Chocolate turns this into a language construct:

```
arena struct Particle { x: Int, y: Int, alive: Bool }

let buf = arena Particle[10000]; // one contiguous allocation, not 10000 heap objects
buf[i].x = buf[i].x + 1;          // compiles directly to MemorySegment.get/set at the right offset
```

No intermediate object is ever materialized for `buf[i]` — field
access compiles straight to the offset-computed memory read/write. For
a system that touches thousands of entities every frame, that's the
difference between one allocation and thousands, and between
GC-tracked objects and a block the GC barely has to think about.
(Honestly disclosed limit: auto-reclaimed via `Arena.ofAuto()`, not yet
a manual-`free` arena — see the ARCHITECTURE.md's own "Off-heap data" section.)

## One compiler, multiple JDK targets — because mod support lag is real

A concrete, common constraint this was built against: a game engine
free to run the newest JDK, alongside mod support for game versions
pinned to older JDKs for stability (a real example: a 1.20.1 mod line
on JDK 17 alongside a 1.21.1 mod line on JDK 21, alongside a JDK-25
engine) — normally forcing either three separate toolchains or writing
every mod to the lowest common denominator forever.

`--target 17|21|25` picks the JDK a given compile targets — classfile
version, and which newer stdlib topics (like `phoenix_virtual` above,
or a construct like `arena struct` that genuinely needs JDK 22+) are
even visible — from the SAME compiler, SAME language, per invocation.
The old mod line keeps compiling exactly as before (default is `17`,
fully backward compatible); the engine and newer mod line get real
value from newer JDK features the moment they're ready for them,
without waiting for the older line to catch up, and without forking
the toolchain to get there.

## Sealed interfaces, exhaustive `match`, and a real `Result<T, E>`

Java's answer to "one of several kinds of thing" is either a class
hierarchy plus `instanceof` chains (no compiler-enforced exhaustiveness
until fairly recent, verbose `sealed`/pattern-match Java versions), or
a plain enum with no payload per variant. Modeling game state machines,
event types, or "this operation can fail in one of these specific
ways" ends up either sprawling or lossy.

Hot Chocolate gives you real tagged-union enums (`enum Result<T, E> {
Ok(T), Err(E) }`-shaped, with real payloads), sealed interfaces with
`match`-by-concrete-type, and the `?` operator for propagating a
`Result` with early return — all checked exhaustively at compile time,
without Java's exception-based error handling (where "what can this
throw" is invisible at a call site unless you go read the source).

## Zero-cost interop with the ecosystem you're already targeting

None of the above requires leaving the JVM game/mod ecosystem. `extern
class`/`extern interface` bindings against real Java classes (the JDK
itself, Minecraft/Forge's own API, any existing `.jar`) compile
directly to `INVOKEVIRTUAL`/`INVOKEINTERFACE`/`INVOKESTATIC` against
the real binary name — no wrapper objects, no reflection at runtime,
classpath-verified signatures at compile time. A Hot Chocolate mod
drops into an existing Forge/Fabric project's build the same way a
Java or Kotlin one does, because at the bytecode level, it is one.

## What this deliberately isn't

Worth stating plainly, because the value proposition above is
strongest when the scope is honest: this is not an attempt to
reimplement Rust's full memory-safety story (no lifetimes, no
`unsafe`/`safe` split — the JVM's GC already owns memory safety, so
move/borrow checking here is scoped to the aliasing/mutation bugs that
actually recur in game code, not a general soundness proof), and it's
not a bid to replace Java/Kotlin/Scala as a general-purpose JVM
language. It's a small, opinionated, niche-scoped language built
because it makes real game/mod code better — concise syntax, real
generics, and compile-time guarantees Java's type system structurally
can't express, on top of full interop with the ecosystem those games
and mods already live in.
